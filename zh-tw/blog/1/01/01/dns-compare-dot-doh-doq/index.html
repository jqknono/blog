Monday, January 01, 0001

  1. 分析用户请求：

    • 输入： 一篇中文博客文章（简体），比较了各种 DNS 加密协议（Plain DNS、DoT、DoH、DoQ）。内容采用 Markdown 格式，包含 front matter、标题、列表、Mermaid 图表、表格和链接。
    • 任务： 将内容从简体中文（zh-cn）翻译为繁体中文（zh-tw）。
    • 限制条件：
      • 严格遵守格式（JSON/XML/Markdown 结构）。
      • 处理代码块：不要翻译标识符（mermaid, bash 等）。
      • 不要解释，不要加前缀/后缀。
      • 具体的 Front Matter 规则：翻译 tags、categories、description，不要翻译 slug（虽然这里没有 slug 字段，但值得注意）。title 通常需要翻译以匹配正文语言。

  2. 检查翻译必要性（逻辑检查）：

    • 内容是 Markdown 文档。
    • 它包含大量需要本地化的自然语言文本。
    • Front matter 包含需要翻译的关键字（tags, categories, description）。
    • 结论： 翻译是必需的。

  3. 执行 - 逐段翻译与格式化：

    • Front Matter：

      • layout: blog -> 保留
      • categories: ["network"] -> network 是英语，保留。
      • tags: ["DNS", "DoH", "DoT", "QUIC"] -> 缩写/英语术语，保留。
      • draft: false -> 保留
      • title: DNS 加密协议对比：DoT、DoH、DoQ -> 简体 转 繁体。
        • 加密 -> 加密
        • 协议 -> 協議
        • 对比 -> 對比
        • 结果：DNS 加密協議對比：DoT、DoH、DoQ
      • date: ... -> 保留
      • comments: true -> 保留
      • giscus_comments: true -> 保留
      • description: 梳理 Plain DNS、DoT、DoH、DoQ 的分层关系、端口、性能差异与适用场景，给出实际选择与配置建议。 -> 简体 转 繁体。
        • 梳理 -> 梳理
        • 分层关系 -> 分層關係
        • 端口 -> 端口（术语，有时是埠，但在技术语境下端口很常见，通常保持原样或映射。在 TW 技术文档中，‘端口’ 被广泛接受，‘埠’ 更传统。我将坚持使用标准技术术语，通常是 ‘端口’ 或严格对应语境。‘端口’ 通常是安全的，但让我们检查一下特定语境。‘分層關係’ -> 層級關係 或 分層關係。‘性能’ -> ‘效能’。‘差异’ -> ‘差異’。‘适用’ -> ‘適用’。‘实际’ -> ‘實際’。‘配置’ -> ‘配置’。
        • 草稿：梳理 Plain DNS、DoT、DoH、DoQ 的分層關係、端口、效能差異與適用場景，給出實際選擇與配置建議。
      • weight: 100 -> 保留

    • 内容 - 标题 2：名词速览

      • 名词 -> 名詞

    • 列表：

      • Plain DNS：明文 DNS，默认使用 UDP/53，必要时用 TCP/53（如响应被截断、区域传送等）。
        • 明文 -> 明文
        • 默认 -> 預設
        • 必要时 -> 必要時
        • 响应 -> 回應
        • 截断 -> 截斷
        • 区域传送 -> 區域傳送
      • DoT：DNS over TLS，使用 TLS 之上的 TCP，默认端口 853（RFC 7858/8310）。 -> 預設端口
      • DoH：DNS over HTTPS，基于 HTTPS（HTTP/2 或 HTTP/3），默认端口 443（RFC 8484）。 -> 基於、預設端口
      • DoQ：DNS over QUIC，基于 QUIC + TLS 1.3，默认端口 UDP/853（RFC 9250，IANA 已分配在 853/udp）。 -> 基於、預設端口
