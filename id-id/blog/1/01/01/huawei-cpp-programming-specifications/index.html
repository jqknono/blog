Aturan 5.2.3 Melarang Referensi Fungsi Eksternal melalui Deklarasi

Hanya dapat menggunakan cara menyertakan header file untuk menggunakan antarmuka atau fungsi yang diberikan oleh modul atau file lain. Melalui deklarasi extern untuk menggunakan antarmuka fungsi eksternal, variabel, mudah menyebabkan deklarasi dan definisi tidak konsisten saat antarmuka eksternal berubah. Selain itu, dependensi implisit ini mudah menyebabkan korosi arsitektur.

Contoh yang tidak sesuai dengan standar:

// Isi a.cpp

extern int Fun();   // Bad: Melalui cara menggunakan fungsi eksternal

void Bar()
{
    int i = Fun();
    ...
}

// Isi b.cpp

int Fun()
{
    // Lakukan sesuatu
}

Harus diubah menjadi:

// Isi a.cpp

#include "b.h"   // Good: Melalui menyertakan header file untuk menggunakan antarmuka .cpp yang diberikan

void Bar()
{
    int i = Fun();
    ...
}

// Isi b.h

int Fun();

// Isi b.cpp

int Fun()
{
    // Lakukan sesuatu
}

Kecuali, ada beberapa skenario yang memerlukan merujuk fungsi dalamnya, tetapi tidak ingin menginvasi kode, dapat menggunakan cara deklarasi extern. Seperti:

  • Untuk unit test terhadap fungsi internal tertentu, dapat melalui deklarasi extern untuk merujuk fungsi yang diuji;
  • Ketika perlu melakukan pengecekan (stub) atau pemrosesan patch terhadap fungsi tertentu, diperbolehkan deklarasi extern fungsi tersebut.

Aturan 5.2.4 Melarang Menyertakan Header File di dalam extern "C"

Menyertakan header file di dalam extern "C" mungkin menyebabkan extern "C" bersarang, beberapa kompiler memiliki batasan lapisan `extern “C””, lapisan terlalu banyak akan menyebabkan kesalahan kompilasi.

Pada pemrograman C, C++ campuran, menyertakan header file di dalam extern "C" mungkin menyebabkan niat header file yang terkandung rusak, seperti aturan ikatan tidak dengan benar diubah.

Contoh, ada dua header file a.h dan b.h:

// Isi a.h

...
#ifdef __cplusplus
void Foo(int);
#define A(value) Foo(value)
#else
void A(int)
#endif

// Isi b.h

...
#ifdef __cplusplus
extern "C" {
#endif

#include "a.h"
void B();

#ifdef __cplusplus
}
#endif

Menggunakan pemrosesor preprocessor C++ untuk mengexpand b.h, akan menghasilkan

extern "C" {
    void Foo(int);
    void B();
}

Menurut niat pembuat a.h, fungsi Foo adalah fungsi C++ bebas, ikatan ikatan linaknya adalah “C++”. Namun, di b.h, karena #include "a.h" ditempatkan di dalam extern "C", ikatan ikatan lin fungsi Foo diubah tidak dengan benar.

Kecuali: Jika dalam lingkungan kompilasi C++, ingin merujuk header file murni C, header file C tersebut tidak memiliki penanda extern "C". Cara non-invasif adalah, di dalam extern “C”` mengakhiri penyertaan header file C.

Saran 5.2.1 Seluruhnya Hindari menggunakan deklarasi sebelumnya, lebih baik melalui #include untuk menyertakan header file

Deklarasi sebelumnya (forward declaration) biasanya merujuk pada deklaraturala murni kelas, template, tanpa menyertakan definisinya.

  • Keuntungan:
    1. Deklarasi sebelumnya dapat menghemat waktu kompilasi, #include berlebihan memaksa kompiler untuk membuka lebih banyak file, memproses lebih banyak input.
    2. Deklarasi sebelumnya dapat menghemat waktu pengulangan kompilasi yang tidak perlu. #include membuat kode terulang di-recompile berkat perubahan di header file yang tidak relevan.
  • Kekurangan:
    1. Deklarasi sebelumnya menyembunyikan dependensi, saat perubahan header file, kode pengguna akan melewati proses pengulangan kompilasi yang diperlukan.
    2. Deklarasi sebelumnya mungkin akan dihancurkan oleh perubahan selanjutnya perpustakaan. Deklarasi sebelumnya template terkadang menghalangi pengembang header file mengubah API-nya. Misalnya memperluas parameter fungsi menambahkan parameter template dengan nilai default bawaan.
    3. Deklarasi sebelumnya yang berasal dari symbol namespace std:: perilaku tidak ditentukan (ditetapkan secara eksplisit dalam standar C++11).
    4. Sekadar untuk dapat deklarasi sebelumnya merefaktor kode (misalnya menggunakan pointer anggota daripada anggota objek) akan membuat kode menjadi lebih lambat dan lebih kompleks.
    5. Sulit menentukan kapan seharusnya menggunakan deklarasi sebelumnya, kapan #include, beberapa skenario saat menukarkan deklarasi sebelumnya dan #include dapat menghasilkan hasil yang tidak terduga.

Jadi kita sebaiknya menghindari penggunaan deklarasi sebelumnya, lebih baik menggunakan #include header file untuk menjamin dependensi.

6 Ruang Lingkup

Namespace

Saran 6.1.1 Untuk variabel, konstanta atau fungsi di file cpp yang tidak perlu diekspor, gunakan anonymous namespace atau static untuk memaketkan

Pada standar C++ 2003, menggunakan static untuk mendeklarasikan variabel fungsi ruang file dianggap deprecated, sehingga lebih disarankan menggunakan anonymous namespace.

Alasan utama seperti berikut:

  1. static di C++ telah diberikan terlalu banyak makna, variabel anggota statis, fungsi anggota statis, variabel global statis, fungsi lokal statis, setiap satu memiliki penanganan khusus.
  2. static hanya dapat menjamin ruang lingkup file variabel, konstanta dan fungsi, tetapi namespace masih dapat mengenkapsulasi tipe data dan sebagainya.
  3. One namespace untuk mengelola ruang lingkup C++, tanpa perlu secara bersamaan menggunakan static dan namespace untuk pengelolaan.
  4. Fungsi static tidak dapat digunakan untuk menginstansiasi template, sedangkan anonymous namespace dapat.

Tapi jangan gunakan anonymous namespace atau static di .h.

// Foo.cpp

namespace {
    const int MAX_COUNT = 20;
    void InternalFun() {};
}

void Foo::Fun()
{
    int i = MAX_COUNT;
   
    InternalFun();
}

Aturan 6.1.1 Jangan menggunakan using untuk mengimpor namespace di atas header file atau sebelum #include

Keterangan: Menggunakan using untuk mengimpor namespace akan memengaruhi kode selanjutnya, mudah menyebabkan benturan simbol, jadi jangan menggunakan using di header file serta di sumber file di atas #include.

Contoh:

// Header file a.h

namespace NamespaceA {
    int Fun(int);
}

// Header file b.h

namespace NamespaceB {
    int Fun(int);
}

using namespace NamespaceB;

void G()
{
    Fun(1);
}

// Sumber code a.cpp

#include "a.h"
using namespace NamespaceA;
#include "b.h"

void main()
{
    G(); // using namespace NamespaceA di atas #include “b.h”, memicu ambigu: NamespaceA::Fun, NamespaceB::Fun pemanggilan tidak jelas
}

Untuk menggunakan using di header file untuk mengimpor simbol tunggal atau definisi alias, diizinkan dalam nama nama modul kustom, tetapi dilarang menggunakan di nama nama global.

// foo.h

#include <fancy/string>
using fancy::string;  // Bad, dilarang mengimpor simbol ke nama nama global

namespace Foo {
    using fancy::string;  // Good, dapat di dalam nama nama modul kustom yang dibuat
    using MyVector = fancy::vector<int>;  // Good, C++11 dapat di nama nama modul kustom untuk mendefinisikan alias
}

Fungsi Global dan Fungsi Anggota Statis

Saran 6.2.1 Prioritas menggunakan namespace untuk mengelola fungsi global, jika dan class memiliki hubungan langsung, dapat menggunakan fungsi anggota statik

Keterangan: Fungsi non-member diletakan di dalam nama namespace dapat menghindari pencemaran nama nama global, juga jangan gunakan metode kelas statik sederhana untuk mengelola fungsi global. Jika fungsi global tertentu memiliki hubungan erat dengan class tertentu, dapat sebagai fungsi anggota statik kelas.

Jika Anda perlu mendefinisikan beberapa fungsi global, digunakan oleh file cpp tertentu, silakan gunakan anonymous namespace untuk mengelolanya.

namespace MyNamespace {
    int Add(int a, int b);
}

class File {
public:
    static File CreateTempFile(const std::string& fileName);
};

Konstanta Global dan Konstanta Anggota Statis

Saran 6.3.1 Prioritas menggunakan namespace untuk mengelola konstanta global, jika dan class memiliki hubungan langsung, dapat menggunakan konstanta anggota statik kelas

Keterangan: Konstanta global diletakan di dalam nama namespace dapat menghindari pencemaran nama nama global, juga jangan gunakan kelas+ konstanta anggota statik untuk mengelola konstanta global secara sederhana. Jika konstanta global tertentu memiliki hubungan erat dengan class tertentu, dapat sebagai konstanta anggota statik kelas.

Jika Anda perlu mendefinisikan beberapa konstanta global, hanya untuk digunakan oleh file cpp tertentu, silakan gunakan anonymous namespace untuk mengelolanya.

namespace MyNamespace {
    const int MAX_SIZE = 100;
}

class File {
public:
    static const std::string SEPARATOR;
};

Variabel Global

Saran 6.4.1 Sebaiknya menghindari penggunaan variabel global, pertimbangkan menggunakan pola Singleton

Keterangan: Variabel global dapat dibaca dan ditulis, sehingga akan menyebabkan kode bisnis dan variabel global ini menghasilkan ketergantungan data.

int g_counter = 0;

// a.cpp
g_counter++;

// b.cpp
g_counter++;

// c.cpp
cout << g_counter << endl;

Menggunakan pola Singleton

class Counter {
public:
    static Counter& GetInstance()
    {
        static Counter counter;
        return counter;
    }  // Implementasi singleton sederhana

    void Increase()
    {
        value_++;
    }
   
    void Print() const
    {
        std::cout << value_ << std::endl;
    }

private:
    Counter() : value_(0) {}

private:
    int value_;
};

// a.cpp
Counter::GetInstance().Increase();

// b.cpp
Counter::GetInstance().Increase();

// c.cpp
Counter::GetInstance().Print();

Setelah mengimplementasikan pola Singleton, telah diimplementasikan satu instans global, dengan efek sama seperti variabel global, dan singleton memberikan pengelasan (encapsulation) yang lebih baik.

Kecuali: Kadang-kadang ruang lingkup variabel global hanya bersifat internal modul, sehingga akan ada banyak instance variabel global di ruang alur proses, setiap modul memiliki satu instans, skenario ini tidak dapat diselesaikan menggunakan pola Singleton.

7 Kelas

Konstruktor, Konstruktor Salin, Penugasan dan Fungsi Pembungkus

Konstruktor, salin, perpindahan dan fungsi pembungkus menyediakan metode pengelolaan siklus hidup objek:

  • Konstruktor (constructor): X()
  • Konstruktor salin (copy constructor): X(const X&)
  • Operasi penugasan salin (copy assignment): operator=(const X&)
  • Konstruktor perpindahan (move constructor): X(X&&) Diberikan C++11
  • Operasi penugasan perpindahan (move assignment): operator=(X&&) Diberikan C++11
  • Fungsi pembungkus (destructor): ~X()

Aturan 7.1.1 Variabel anggota kelas harus diinisialisasi secara eksplisit

Keterangan: Jika kelas memiliki variabel anggota, tidak mendefinisikan konstruktor, juga tidak mendefinisikan konstruktor default, kompiler akan secara otomatis menghasilkan konstruktor, namun konstruktor yang dihasilkan kompiler tidak akan melakukan inisialisasi pada variabel anggota, status objek berada dalam ketidakpastian.

Kecuali:

  • Jika variabel anggota kelas memiliki fungsi konstruktor default, maka tidak perlu inisialisasi eksplisit.

Contoh: Seperti kode berikut tidak ada konstruktor, data pribadi tidak dapat diinisialisasi:

class Message {
public:
    void ProcessOutMsg()
    {
        //…
    }

private:
    unsigned int msgID_;
    unsigned int msgLength_;
    unsigned char* msgBuffer_;
    std::string someIdentifier_;
};

Message message;   // variabel anggota message tidak diinisialisasi
message.ProcessOutMsg();   // penggunaan berikut berisiko

// Oleh karena itu, perlu mendefinisikan konstruktor default, seperti berikut:
class Message {
public:
    Message() : msgID_(0), msgLength_(0), msgBuffer_(nullptr)
    {
    }

    void ProcessOutMsg()
    {
        // …
    }

private:
    unsigned int msgID_;
    unsigned int msgLength_;
    unsigned char* msgBuffer_;
    std::string someIdentifier_; // memiliki fungsi konstruktor default, tidak perlu inisialisasi eksplisit
};

Saran 7.1.1 Prioritas menggunakan inisialisasi saat deklarasi (C++11) dan daftar inisialisasi konstruktor

Keterangan: Inisialisasi saat deklarasi C++11 dapat langsung terlihat nilai awal anggota, sebaiknya digunakan. Jika nilai inisialisasi anggota dan konstruktor berkaitan, atau tidak mendukung C++11, sebaiknya digunakan daftar inisialisasi konstruktor untuk menginisialisasi anggota. Berbanding dengan pada badan konstruktor untuk memberikan nilai anggota, kode daftar inisialisasi lebih ringan, performa eksekusi lebih baik, dan dapat untuk inisialisasi anggota const dan referensi.

class Message {
public:
    Message() : msgLength_(0)  // Good, prioritaskan penggunaan daftar inisialisasi
    {
        msgBuffer_ = nullptr;  // Bad, tidak disarankan memberikan nilai di dalam badan konstruktor
    }
   
private:
    unsigned int msgID_{0};  // Good, penggunaan di C++11
    unsigned int msgLength_;
    unsigned char* msgBuffer_;
}

Aturan 7.1.2 Untuk menghindari konversi implisit, deklarasikan konstruktor satu parameter sebagai explicit

Keterangan: Jika konstruktor satu parameter tidak digunakan explicit, maka akan menjadi fungsi konversi implisit.

Contoh:

class Foo {
public:
    explicit Foo(const string& name): name_(name)
    {
    }
private:
    string name_;
};


void ProcessFoo(const Foo& foo){
}

int main(void)
{
    std::string test = "test";
    ProcessFoo(test);  // Kompilasi tidak melalui
    return 0;
}

Kode di atas tidak melalui kompilasi, karena ProcessFoo memerlukan parameter tipe Foo, tipe yang dimasukkan string tidak cocok.

Jika dikonstruktor Foo dikurangi kunci explicit, maka pemanggilan ProcessFoo dengan memasukkan string akan memicu konversi implisit, menghasilkan objek Foo sementara. Biasanya konversi implisit ini memukul kebingungan, dan mudah menyembunyikan Bug, serta mendapatkan konversi tipe yang tidak diinginkan. Oleh karena itu untuk konstruktor satu parameter dikehendaki deklarasi explicit.

Aturan 7.1.3 Jika tidak perlu konstruktor salin, operasi penugasan / konstruktor perpindahan, operasi penugasan, sebaiknya dilarang secara eksplisit

Keterangan: Jika pengguna tidak mendefinisikan, kompiler secara default akan menghasilkan konstruktor salin dan operasi penugasan salin, konstruktor perpindahan dan operasi penugasan perpindahan (fungsi semantik perpindahan C++11 kemudian ada). Jika kita tidak ingin menggunakan konstruktor salin, atau operasi penugasan, sebaiknya menolak secara eksplisit:

  1. Menetapkan konstruktor salin atau operasi penugasan menjadi private, dan tidak mengimplementasikan:
class Foo {
private:
    Foo(const Foo&);
    Foo& operator=(const Foo&);
};
  1. Menggunakan delete yang disediakan C++11, lihat bagian C++ modern berikut.
  2. Disarankan mewarisi NoCopyable, NoMovable, melarang menggunakan makro DISALLOW_COPY_AND_MOVE, DISALLOW_COPY, DISALLOW_MOVE dll.
class Foo : public NoCopyable, public NoMovable {
};

Implementasi NoCopyable dan NoMovable:

class NoCopyable {
public:
    NoCopyable() = default;
    NoCopyable(const NoCopyable&) = delete;
    NoCopyable& operator = (NoCopyable&) = delete;
};

class NoMovable {
public:
    NoMovable() = default;
    NoMovable(NoMovable&&) noexcept = delete;
    NoMovable& operator = (NoMovable&&) noexcept = delete;
}

Aturan 7.1.4 Konstruktor salin dan operasi penugasan salin seharusnya muncul berpasangan atau dilarang

Konstruktor salin dan operasi penugasan salin memiliki semantik salin, seharusnya muncul berpasangan atau dilarang.

// Muncul berpasangan
class Foo {
public:
    ...
    Foo(const Foo&);
    Foo& operator=(const Foo&);
    ...
};

// Muncul default, C++11 mendukung
class Foo {
public:
    Foo(const Foo&) = default;
    Foo& operator=(const Foo&) = default;
};

// Muncul dilarang, C++11 dapat menggunakan `delete`
class Foo {
private:
    Foo(const Foo&);
    Foo& operator=(const Foo&);
};

Aturan 7.1.5 Konstruktor perpindahan dan operasi penugasan perpindahan seharusnya muncul berpasangan atau dilarang

Pada C++11 ditambah operasi move. Jika kelas tertentu memerlukan operasi perpindahan, maka perlu mengimplementasikan konstruktor perpindahan dan operasi penugasan perpindahan.

Konstruktor perpindahan dan operasi penugasan perpindahan memiliki semantik semantik perpindahan, seharusnya muncul berpasangan atau dilarang.

// Muncul berpasangan
class Foo {
public:
    ...
    Foo(Foo&&);
    Foo& operator=(Foo&&);
    ...
};

// Muncul default, C++11 mendukung
class Foo {
public:
    Foo(Foo&&) = default;
    Foo& operator=(Foo&&) = default;
};

// Muncul dilarang, menggunakan `delete` C++11
class Foo {
public:
    Foo(Foo&&) = delete;
    Foo& operator=(Foo&&) = delete;
};

Aturan 7.1.6 Dilarang memanggil fungsi virtual di dalam konstruktor dan fungsi pembungkus

Keterangan: Memanggil fungsi virtual dari objek saat ini di dalam konstruktor dan fungsi pembungkus, akan menyebabkan perilaku polimorfis yang tidak sepenuhnya diimplementasikan. Pada C++, satu kelas induk hanya dibangun satu kali.

Contoh: Kelas Base adalah kelas induk, Sub adalah kelas turunan

class Base {                      
public:               
    Base();
    virtual void Log() = 0;    // Fungsi log berbeda-beda untuk kelas turunan yang berbeda
};

Base::Base()         // Konstruktor kelas induk
{
    Log();           // Memanggil fungsi virtual Log
}                                                 

class Sub : public Base {      
public:
    virtual void Log();         
};

Ketika melakukan pernyataan: Sub sub; akan terlebih dahulu mengeksekusi konstruktor Sub, namun pertama kali memanggil konstruktor Base, karena konstruktor Base memanggil fungsi virtual Log, saat itu Log masih versi kelas induk, hanya setelah konstruktor Base selesai, baru akan menyelesaikan konstruktor kelas turunan, sehingga menyebabkan perilaku polimorfis yang tidak sepenuhnya diimplementasikan. Hal yang sama juga berlaku untuk fungsi pembungkus.

Aturan 7.1.7 Konstruktor salin, operasi penugasan salin, konstruktor perpindahan, operasi penugasan perpindahan dalam kelas polimorfis harus menjadi fungsi non-public atau fungsi delete

Jika mengassign objek kelas turunan langsung ke objek kelas induk, akan terjadi pemotongan (slice), hanya mengkopi atau memindahkan bagian kelas induk, mengganggu perilaku polimorfis. [Counter-example] Kode berikut di mana kelas induk tidak mendefinisikan konstruktor salin atau operasi penugasan salin, kompiler akan secara otomatis menghasilkan keduanya, jika objek kelas turunan diassign ke objek kelas induk justru terjadi pemotongan. Bisa mengurangi konstruktor salin atau operasi penugasan salin dideklarasikan sebagai private, dan tidak diimplementasikan, atau dideklarasikan delete, kompiler dapat mendeteksi perilaku assignasi kelas ini.

class Base {                      
public:               
    Base() = default;
    virtual ~Base() = default;
    ....
    virtual void Fun() { std::cout << "Base" << std::endl; }
};

class Derived : public Base {
    ....
    void Fun() override { std::cout << "Derived" << std::endl; }
};

void Foo(const Base &base)
{
    Base other = base; // Tidak sesuai: terjadi pemotongan
    other.Fun(); // Memanggil fungsi Fun kelas Base
}

Derived d;
Foo(d); // Diteruskan objek kelas turunan

Warisan

Aturan 7.2.1 Fungsi pembungkus kelas induk seharusnya dideklarasikan sebagai virtual, kelas yang tidak ingin diwariskan seharusnya dideklarasikan sebagai final

Keterangan: Hanya jika fungsi pembungkus kelas induk adalah virtual, saat pemanggilan melalui polimorfis dapat menjamin fungsi pembungkus kelas turunan dipanggil.

Contoh: Fungsi pembungkus kelas induk tidak dideklarasikan sebagai virtual menyebabkan kebocoran memori.

class Base {
public:
    virtual std::string getVersion() = 0;
   
    ~Base()
    {

Warisan Ganda

Dalam pengembangan nyata penggunaan warisan ganda adalah skenario yang relatif sedikit, karena adanya masalah tipikal berikut pada saat menggunakan warisan ganda:

  1. Warisan berkepinggayaan (diamond inheritance) yang membawa data duplikat, serta ketidakjelasan nama. Oleh karena itu, C++ memperkenalkan virtual inheritance untuk menyelesaikan masalah ini;
  2. Meski bukan warisan berkepinggayaan, nama beberapa kelas induk juga mungkin bertentangan, sehingga menyebabkan ketidakjelasan nama;
  3. Jika kelas turunan perlu memperluas atau mengubah metode beberapa kelas induk, menyebabkan tanggung jawab kelas turunan tidak jelas, semantik kabut;
  4. Berbanding dengan delegasi, warisan adalah kompleks white-box reuse, yaitu kelas turunan dapat mengakses protected anggota kelas induk, ini akan menyebabkan ketergantungan yang lebih kuat. Warisan ganda, berbanding dengan warisan tunggal, duekrut menghasilkan ketergantungan yang lebih kuat.

Warisan ganda memiliki keuntungan berikut: Warisan ganda menyediakan cara lebih sederhana untuk melakukan kombinasi untuk merealisasikan beberapa antarmuka atau penggabungan kelas.

Jadi, untuk warisan ganda hanya dalam kasus berikut diizinkan untuk digunakan.

Saran 7.3.1 Menggunakan warisan ganda untuk pemisahan antarmika dan kombinasi peran

Jika kelas tertentu perlu merealisasikan beberapa antarmuka, dapat melalui warisan ganda menggabungkan beberapa antarmika yang terpisah, mirip bahasa Scala traits campuran.

};

Di perpustakaan standar C++ juga ada contoh implementasi yang mirip:

Overload

Operasi operator overload harus memiliki alasan yang cukup, dan jangan mengubah semantik operator asli, misalnya jangan menggunakan operator ‘+’ untuk melakukan operasi pengurangan.

Overload operator membuat kode lebih intuitif, namun juga memiliki beberapa kekurangan:

  • Mengabaikan intuisi, mengira operasi ini dan tipe bawaan sama adalah performa tinggi, mengabaikan kemungkinan penurunan performa;
  • saat penelusuran masalah, tidak intuitif, mencari nama fungsi lebih jelas daripada mencari operasi.
  • Overload operator jika perilaku didefinisikan tidak intuitif (misalnya menggunakan operator ‘+’ untuk melakukan operasi pengurangan), akan membuat kode menjadi membingungkan.
  • Overload operator penugasan menyebabkan konversi implisit yang tersembunyi bug yang sangat dalam. Dapat mendefinisikan fungsi seperti Equals(), CopyFrom() sebagai gantian operator =, ==.

Desain Fungsi

Aturan 8.1.1 Hindari fungsi terlalu panjang, fungsi tidak melebihi 50 baris (non-komentar non-komentar)

Fungsi seharusnya dapat ditampilkan layar penuh (50 baris atau kurang), melakukan satu hal, dan melakukan hal itu dengan baik.

Fungsi terlalu panjang seringkali berarti fungsi memiliki fungsi tidak satu, terlalu kompleks, atau terlalu menampakkan detail, belum dilakukan abstraksi lebih lanjut.

Kecuali: Beberapa fungsi algoritma implementasi, karena agregat algoritma dan fungsi fitur penuh, mungkin akan melebihi 50 baris.

Meski fungsi panjang sekarang bekerja sangat baik, segera ada orang mengubahnya, kemungkinan muncul masalah baru, bahkan menyebabkan bug yang sulit dideteksi.

Saran memecahnya menjadi beberapa fungsi yang lebih singkat dan mudah dikelola, untuk memudahkan orang lain membaca dan mengubah kode.

Saran 8.2.1 Fungsi inline tidak melebihi 10 baris (non-komentar non-komentar)

Keterangan: Fungsi inline memiliki karakteristik umum fungsi, berbeda dengan fungsi umum hanya dalam penanganan pemanggilan fungsi. Ketika pemanggilan fungsi umumnya, perlualihkan hak eksekusi ke fungsi yang dipanggil, lalu kembali ke fungsi yang memanggil; sedangkan fungsa inline saat pemanggilan, adalah mengganti ekspresi pemanggilan dengan badan fungsi inline.

Fungsi inline hanya cocok untuk fungsi kecil 1-10 baris. Untuk fungsi besar yang berisi banyak pernyataan, overhead pemanggilan dan kembali fungsi relatif mikro, tidak ada alasan untuk menggunakan fungsi inline, mayoritas kompiler akan menolak cara inline, dan memilih cara pemanggilan fungsi umum.

Jika fungsi inline berisi struktur kontrol kompleks, seperti perulangan, cabang (switch), try-catch dan sebagainya, mayoritas kompiler akan dianggap fungsi ini seolah-olah fungsi umum.

Fungsi virtual, fungsi rekursif tidak dapat digunakan sebagai fungsi inline.

Saran 8.3.1 Parameter fungsi gunakan referensi menggantikan pointer

Keterangan: Referensi lebih aman daripada pointer, karena pasti non-kosong, dan pasti tidak akan menunjuk ke target lain; referensi tidak perlu memeriksa pointer NULL ilegal.

Jika pengembangan produk berdasarkan platform lama, maka lebih tunduk urutan penanganan platform yang ada.

Pilih const untuk menghindari parameter dimodifikasi, membuat pembaca kode jelas parameter tidak dimodifikasi, dapat meningkatkan readability kode secara signifikan.

Kecuali: Saat parameter masukan adalah array dengan panjang yang tidak diketahui pada waktu kompilasi, dapat menggunakan pointer daripada referensi.

Saran 8.3.2 Gunakan parameter tipe kuat, hindari penggunaan void*

Meskipun berbagai bahasa menghadap tipe kuat dan tipe lemah memiliki pandangan masing-masing, umumnya dianggap C/C++ adalah bahasa tipe kuat, karena kita menggunakan bahasa tipe kuat, seharusnya menjaga gaya ini.

9 Khusus C++

Konstanta dan Inisialisasi

Nilai yang tidak berubah lebih mudah dipahami, dipantau dan dianalisis, seharusnya se mungkin menggunakan konstanta menggantikan variabel, saat mendefinisikan nilai, seharusnya membuat const sebagai opsi default.

Aturan 9.1.1 Dilarang menggunakan makro untuk merujuk konstanta

Keterangan: Makro adalah penggantian teks sederhana, dilakukan pada fase preprocessor, saat error eksekusi langsung menampilkan nilai yang sesuai; saat debugging juga menampilkan nilai, bukan nama makro; makro tidak memiliki pengecekan tipe, tidak aman; makro tidak memiliki ruang lingkup.

#define MAX_MSISDN_LEN 20    // Tidak baik

// Gunakan konstanta C++
const int MAX_MSISDN_LEN = 20; // Baik

// Untuk C++11 ke atas, dapat menggunakan constexpr
constexpr int MAX_MSISDN_LEN = 20;

Saran 9.1.1 sekumpulan konstanta integer yang berkaitan harus didefinisikan sebagai enum

Keterangan: Enum lebih aman daripada #define atau const int. Kompilator akan memeriksa apakah nilai parameter berada dalam rentang nilai enum, menghindari kesalahan terjadi.

// Contoh yang baik:
enum Week {
    SUNDAY,
    MONDAY,
    TUESDAY,
    WEDNESDAY,
    THURSDAY,
    FRIDAY,
    SATURDAY
};

enum Color {
    RED,
    BLACK,
    BLUE
};

void ColorizeCalendar(Week today, Color color);

ColorizeCalendar(BLUE, SUNDAY); // Kompilasi error, tipe parameter salah

// Contoh yang tidak baik:
const int SUNDAY = 0;
const int MONDAY = 1;

const int BLACK  = 0;
const int BLUE   = 1;

bool ColorizeCalendar(int today, int color);
ColorizeCalendar(BLUE, SUNDAY); // Tidak akan error

Saat nilai enum perlu sesuai dengan nilai konkret, harus pada saat deklarasi memberikan nilai. Jika tidak perlu nilai eksplisit, hindari memberikan nilai, untuk menghindari upaya pemeliharaan berulang (menambah, menghapus anggota).

// Contoh yang baik: Nilai ID perangkat yang didefinisikan di protokol A, untuk mengidentifikasi tipe perangkat
enum DeviceType {
    DEV_UNKNOWN = -1,
    DEV_DSMP = 0,
    DEV_ISMG = 1,
    DEV_WAPPORTAL = 2
};

Penggunaan dalam, hanya untuk klasifikasi, seharusnya tidak seharusnya melakukan inisialisasi nilai eksplisit.

// Contoh yang baik: Definisi enum status sesi yang digunakan di program untuk mengidentifikasi status sesi
enum SessionState {
    INIT,
    CLOSED,
    WAITING_FOR_RESPONSE
};

Seharusnya menghindari nilai enum duplikat, jika harus duplikat juga gunakan enum yang sudah didefinisikan untuk memperbaiki

enum RTCPType {

Aturan 9.1.2 Dilarang menggunakan angka iblis

Angka iblis bermakna angka yang sul dipahami, sul dipahami.

Angka iblis bukanlah konsep hitam-putih, ada tingkat sul dipahami. Contoh angka 12, pada konteks berbeda situasi berbeda: type = 12; justru sul dipahami, tetapi monthsCount = yearsCount * 12; justru dipahami.

Angka 0 terkadang juga angka iblis, misalnya status = 0; tidak dapat mengekspresikan status apa.

Solusi: Untuk angka yang digunakan lokal, dapat menambahkan komentar penjelasan. Untuk angka yang digunakan berulang, harus mendefinisikan konstanta const, dan melalui nama simbol auto-comment.

Dilarang muncul situasi berikut: Tanpa melalui simbol untuk menjelaskan makna angka, seperti const int ZERO = 0 Nama simbol membatasi nilai ambilnya, seperti const int XX_TIMER_INTERVAL_300MS = 300, langsung gunakan XX_TIMER_INTERVAL_MS untuk menandakan konstanta ini adalah interval timer detik.

Aturan 9.1.3 Konstanta seharusnya memiliki tanggung jawab tunggal

Keterangan: Satu konstanta hanya digunakan untuk merepresentasikan satu fungsi tertentu, yaitu satu konstanta tidak boleh memiliki banyak tujuan.

// Contoh yang baik: Protokol A dan protokol B, panjang nomor telepon (MSISDN) keduanya 20.
const unsigned int A_MAX_MSISDN_LEN = 20;
const unsigned int B_MAX_MSISDN_LEN = 20;

// atau menggunakan nama namespace yang berbeda:
namespace Namespace1 {
    const unsigned int MAX_MSISDN_LEN = 20;
}

namespace Namespace2 {
    const unsigned int MAX_MSISDN_LEN = 20;
}

Aturan 9.1.4 Dilarang menggunakan memcpy_s, memset_s untuk inisialisasi objek non-POD

Keterangan: POD adalah singkatan Plain Old Data, konsep yang diintroduksikan di standar C++ 98 (ISO/IEC 14882, first edition, 1998-09-01), tipe POD meliputi int, char, float, double, enumeration, void, pointer dan tipe primitif lainnya serta tipe agregat, tidak dapat menggunakan enkapsulasi dan fitur berorientasi objek (seperti konstruktor/penugasan/pembungkus pengguna definisikan, kelas dasar, fungsi virtual).

Karena tipe non-POD misalnya kelas non-agregat, kemungkinan ada fungsi virtual, layout memori tidak pasti, bergantung kompiler, penyalahgunakan operasi memori menyalin mungkin menyebabkan masalah serius.

Bahkan untuk kelas agregat, penggunaan menyalin memori langsung dan perbandingan, menghancurkan perlindungan informasi dan perlindungan data, tidak disarankan operasi memcpy_s, memset_s.

Untuk penjelasan POD lihat lampiran.

Saran 9.1.2 Variabel dideklarasikan saat digunakan dan diinisialisasi

Keterangan: Variabel sebelum digunakan belum diberi nilai, adalah kesalahan pemrograman tingkat rendah yang umum. Mendeklarasikan variabel saat digunakan dan sekaligus diinisialisasi, sangat memudahkan menghindari kesalahan jenis rendah ini.

Mendeklarasikan semua variabel di posisi awal fungsi, kemudian digunakan variabel, ruang lingkup menutupi seluruh implementasi fungsi, mudah menyebabkan masalah berikut:

  • kode sul dipahami dan dipelihara: variabel didefinisikan dan digunakan terpisah.
  • variabel sul diinisialisasi dengan wajar: di posisi awal fungsi, seringkali tidak ada informasi cukup untuk inisialisasi variabel, seringkali digunakan nilai kosong default (misalnya nol) untuk inisialisasi variabel, ini biasanya adalah pemborosan, jika variabel digunakan sebelum diberikan nilai yang efektif, masih akan menyebabkan kesalahan.

Menurut prinsip ruang lingkup variabel paling minim dan prinsip deklarasi dekat, kode lebih mudah dibaca, memudahkan mengetahui tipe variabel dan nilai inisialisasi. Khususnya, sebaiknya menggunakan cara inisialisasi menggantikan deklarasi lalu penugasan.

// Contoh yang buruk: Deklarasi dan inisialisasi dipisahkan
string name;        // Deklarasi tanpa inisialisasi: memanggil konstruktor default
name = "zhangsan";  // Kemudian memanggil operasi penugasan; deklarasi dan definisi di tempat yang berbeda, dipahami relatif sulit

// Contoh yang baik: Deklarasi dan inisialisasi terintegrasi, dipahami relatif mudah
string name("zhangsan");  // Memanggil konstruktor

Ekspresi

Aturan 9.2.1 Ekspresi yang mengandung operasi increment atau decrement variabel dilarang lagi merujuk variabel tersebut

Ekspresi yang mengandung operasi increment atau decrement variabel, jika lagi merujuk variabel tersebut, hasilnya dalam standar C++ tidak ditentukan secara eksplisit. Setiap kompiler atau versi kompiler yang sama mungkin implementasi tidak konsisten.

Untuk portabilitas yang lebih baik, seharusnya tidak membuat asumsi apapun tentang urutan operasi.

Catatan, masalah urutan operasi tidak dapat diselesaikan dengan tanda kurung, karena ini bukan masalah prioritas.

Contoh:

x = b[i] + i++; // Bad: operasi b[i] dengan i++, urutan tidak jelas

Cara yang benar adalah meletakkan operasi increment atau decrement satu baris terpisah:

x = b[i] + i;
i++;            // Good: satu baris terpisah

Parameter fungsi

Func(i++, i);   // Bad: saat memparameter kedua tidak pasti operasi increment sudah terjadi atau tidak

Cara yang benar

i++;            // Good: satu baris terpisah
x = Func(i, i);

Aturan 9.2.2 Switch statement harus memiliki branch default

Sebagian besar kasus, switch statement harus memiliki branch default, untuk memastikan saat label case terlewat ditangani dapat memiliki perilaku default.

Kecuali: Jika variabel kondisi switch adalah tipe enum, dan case branch menutup semua nilai, maka menambahkan branch default sedikit redundan. Kompilator modern semua memiliki kemampuan untuk memeriksa apakah di dalam switch statement ada case branch yang terlewat nilai enum tertentu, akan ada peringatan (warning) sesuai.

enum Color {
    RED = 0,
    BLUE
};

// Karena variabel kondisi switch adalah nilai enum, di sini dapat tidak menambahkan branch default
switch (color) {
    case RED:
        DoRedThing();
        break;
    case BLUE:
        DoBlueThing();
        ...
        break;
}

Saran 9.2.1 Ekspresi perbandingan, seharusnya mengikuti prinsip miring ke kiri bergantung perubahan, miring ke kanan bergantung tidak berubah

Saat variabel dibandingkan dengan konstanta, jika konstanta diletakkan di kiri, seperti if (MAX == v) tidak sesuai dengan kebiasaan membaca, sedangkan if (MAX > v) lebih sul dipahami.

Seharusnya mengikuti kebiasaan membaca manusia, ekspresi normal, letakkan konstanta di kanan.

Tulislah seperti berikut:

if (value == MAX) {

}

if (value < MAX) {

}

Ada kasus khusus, seperti: if (MIN < value && value < MAX) digunakan untuk mendeskripsikan interval, di bagian awal konstanta di kiri.

Jangan khawatir if (value = MAX) salah ketik menjadi =, karena if (value = MAX) akan ada peringatan kompilasi, alat statis cek kode juga akan melaporkan kesalahan. Biarkan alat menyelesaikan masalah ketik salah, kode harus mengutamakan readability.

Saran 9.2.2 Gunakan tanda kurung untuk menjelaskan prioritas operator

Gunakan tanda kurung untuk menjelaskan prioritas operator, menghindari karena prioritas default tidak sesuai dengan pemikiran desain menyebabkan program salah; sekaligus kode lebih jelas dan bisa dibaca, namun terlalu banyak tanda kurung akan membagi kode sehingga readability menurun. Berikut adalah saran penggunaan tanda kurung.

  • Operator biner dan lebih dari, jika melibatkan banyak operator, seharusnya gunakan tanda kurung
x = a + b + c;         /* operator sama, dapat tidak menambahkan tanda kurung */
x = Foo(a + b, c);     /* di kedua sisi tanda koma ekspresi, tidak perlu tanda kurung */
x = 1 << (2 + 3);      /* operator berbeda, perlu tanda kurung */
x = a + (b / 5);       /* operator berbeda, perlu tanda kurung */
x = (a == b) ? a : (a – b);    /* operator berbeda, perlu tanda kurung */

Konversi Tipe

Hindari menggunakan branch tipe untuk menyesuaikan perilaku: penggunaan branch tipe untuk menyesuaikan perilaku mudah salah, adalah tanda mencoba menulis C dengan C++. Ini adalah teknik yang tidak fleksibel, saat menambahkan tipe baru, jika lupa mengubah semua branch, kompiler juga tidak akan memberitahu.

Gunakan template dan fungsi virtual, biarkan tipe sendiri bukanlah kode yang memanggil mereka yang menentukan perilaku.

Saran menghindari konversi tipe, kita dalam desain tipe kelas harus mempertimbangkan tipe data apa yang sesuai, bukan seharusnya terlalu banyak menggunakan konversi tipe untuk menyelesaikan masalah. Saat mendesain tipe dasar tertentu, seharusnya mempertimbangkan:

  • Apakah tidak bersifat tanda atau bersifat tanda
  • Apakah cocok untuk float atau double
  • Apakah menggunakan int8, int16, int32 atau int64, menentukan panjang integer

Namun kita tidak dapat melarang penggunaan konversi tipe, karena C++ adalah bahasa pemrograman berorientasi mesin, melibatkan alamat pointer, dan kita akan berinteraksi dengan berbagai API pihak ketiga atau bawah ini, desain tipe mereka mungkin tidak rational, dalam proses adaptasi ini sangat mudah muncul konversi tipe.

Kecuali: Saat memanggil fungsi tertentu, jika kita tidak ingin menangani hasil fungsi, pertama harus mempertimbangkan apakah pilihan terbaik. Jika memang tidak ingin menangani nilai balik fungsi, dapat menggunakan konversi (void) untuk menyelesaikan.

    ...
}

// Isi b.cpp

{

void Bar()
{

    ...

}

Kecuali, ada beberapa skenario yang memerlukan merujuk fungsi dalamnya, tetapi tidak ingin menginvasi kode, dapat menggunakan cara deklarasi extern. Seperti:

  • Untuk unit test terhadap fungsi internal tertentu, dapat melalui deklarasi extern untuk merujuk fungsi yang diuji;

Aturan 5.2.4 Melarang Menyertakan Header File di dalam extern "C"

Menyertakan header file di dalam extern "C" mungkin menyebabkan extern "C" bersarang, beberapa kompiler memiliki batasan lapisan `extern “C””, lapisan terlalu banyak akan menyebabkan kesalahan kompilasi.

Pada pemrograman C, C++ campuran, menyertakan header file di dalam extern "C" mungkin menyebabkan niat header file yang terkandung rusak, seperti aturan ikatan tidak dengan benar diubah.

Contoh, ada dua header file a.h dan b.h:

// Isi a.h

...
#ifdef __cplusplus
void Foo(int);
#define A(value) Foo(value)
#else
void A(int)
#endif

// Isi b.h

...
#ifdef __cplusplus
extern "C" {
#endif

#include "a.h"
void B();

#ifdef __cplusplus
}
#endif

Menggunakan pemrosesor preprocessor C++ untuk mengexpand b.h, akan menghasilkan

extern "C" {
    void Foo(int);
    void B();
}

Menurut niat pembuat a.h, fungsi Foo adalah fungsi C++ bebas, ikatan ikatan linaknya adalah “C++”. Namun, di b.h, karena #include "a.h" ditempatkan di dalam extern "C", ikatan ikatan lin fungsi Foo diubah tidak dengan benar.

Kecuali: Jika dalam lingkungan kompilasi C++, ingin merujuk header file murni C, header file C tersebut tidak memiliki penanda extern "C". Cara non-invasif adalah, di dalam extern “C”` mengakhiri penyertaan header file C.

Saran 5.2.1 Seluruhnya Hindari menggunakan deklarasi sebelumnya, lebih baik melalui #include untuk menyertakan header file

Deklarasi sebelumnya (forward declaration) biasanya merujuk pada deklaraturala murni kelas, template, tanpa menyertakan definisinya.

  • Keuntungan:
    1. Deklarasi sebelumnya dapat menghemat waktu kompilasi, #include berlebihan memaksa kompiler untuk membuka lebih banyak file, memproses lebih banyak input.
    2. Deklarasi sebelumnya dapat menghemat waktu pengulangan kompilasi yang tidak perlu. #include membuat kode terulang di-recompile berkat perubahan di header file yang tidak relevan.
  • Kekurangan:
    1. Deklarasi sebelumnya menyembunyikan dependensi, saat perubahan header file, kode pengguna akan melewati proses pengulangan kompilasi yang diperlukan.
    2. Deklarasi sebelumnya mungkin akan dihancurkan oleh perubahan selanjutnya perpustakaan. Deklarasi sebelumnya template terkadang menghalangi pengembang header file mengubah API-nya. Misalnya memperluas parameter fungsi menambahkan parameter template dengan nilai default bawaan.
    3. Deklarasi sebelumnya yang berasal dari symbol namespace std:: perilaku tidak ditentukan (ditetapkan secara eksplisit dalam standar C++11).
    4. Sekadar untuk dapat deklarasi sebelumnya merefaktor kode (misalnya menggunakan pointer anggota daripada anggota objek) akan membuat kode menjadi lebih lambat dan lebih kompleks.
    5. Sulit menentukan kapan seharusnya menggunakan deklarasi sebelumnya, kapan #include, beberapa skenario saat menukarkan deklarasi sebelumnya dan #include dapat menghasilkan hasil yang tidak terduga.

Jadi kita sebaiknya menghindari penggunaan deklarasi sebelumnya, lebih baik menggunakan #include header file untuk menjamin dependensi.

Namespace

Saran 6.1.1 Untuk variabel, konstanta atau fungsi di file cpp yang tidak perlu diekspor, gunakan anonymous namespace atau static untuk memaketkan

Pada standar C++ 2003, menggunakan static untuk mendeklarasikan variabel fungsi ruang file dianggap deprecated, sehingga lebih disarankan menggunakan anonymous namespace.

Alasan utama seperti berikut:

  1. static di C++ telah diberikan terlalu banyak makna, variabel anggota statis, fungsi anggota statis, variabel global statis, fungsi lokal statis, setiap satu memiliki penanganan khusus.
  2. static hanya dapat menjamin ruang lingkup file variabel, konstanta dan fungsi, tetapi namespace masih dapat mengenkapsulasi tipe data dan sebagainya.
  3. One namespace untuk mengelola ruang lingkup C++, tanpa perlu secara bersamaan menggunakan static dan namespace untuk pengelolaan.
  4. Fungsi static tidak dapat digunakan untuk menginstansiasi template, sedangkan anonymous namespace dapat.

Tapi jangan gunakan anonymous namespace atau static di .h.

// Foo.cpp

namespace {
    const int MAX_COUNT = 20;
    void InternalFun() {};
}

void Foo::Fun()
{
    int i = MAX_COUNT;
   
    InternalFun();
}

Aturan 6.1.1 Jangan menggunakan using untuk mengimpor namespace di atas header file atau sebelum #include

Keterangan: Menggunakan using untuk mengimpor namespace akan memengaruhi kode selanjutnya, mudah menyebabkan benturan simbol, jadi jangan menggunakan using di header file serta di sumber file di atas #include.

Contoh:

// Header file a.h

namespace NamespaceA {
    int Fun(int);
}

// Header file b.h

namespace NamespaceB {
    int Fun(int);
}

using namespace NamespaceB;

void G()
{
    Fun(1);
}

// Sumber code a.cpp

#include "a.h"
using namespace NamespaceA;
#include "b.h"

void main()
{
    G(); // using namespace NamespaceA di atas #include “b.h”, memicu ambigu: NamespaceA::Fun, NamespaceB::Fun pemanggilan tidak jelas
}

Untuk menggunakan using di header file untuk mengimpor simbol tunggal atau definisi alias, diizinkan dalam nama nama modul kustom, tetapi dilarang menggunakan di nama nama global.

// foo.h

#include <fancy/string>
using fancy::string;  // Bad, dilarang mengimpor simbol ke nama nama global

namespace Foo {
    using fancy::string;  // Good, dapat di dalam nama nama modul kustom yang dibuat
    using MyVector = fancy::vector<int>;  // Good, C++11 dapat di nama nama modul kustom untuk mendefinisikan alias
}

Keterangan: Fungsi non-member diletika di dalam nama namespace dapat menghindari pencemaran nama nama global, juga jangan gunakan metode kelas statik sederhana untuk mengelola fungsi global. Variabel Global

Saran 6.4.1 Sebaiknya menghindari penggunaan variabel global, pertimbangkan menggunakan pola Singleton

Keterangan: Variabel global dapat dibaca dan ditulis, sehingga akan menyebabkan kode bisnis dan variabel global ini menghasilkan ketergantungan data.

int g_counter = 0;

// a.cpp
g_counter++;

// b.cpp
g_counter++;

// c.cpp
cout << g_counter << endl;

Menggunakan pola Singleton

class Counter {
public:
    static Counter& GetInstance()
    {
        static Counter counter;
        return counter;
    }  // Implementasi singleton sederhana

    void Increase()
    {
        value_++;
    }
   
    void Print() const
    {
        std::cout << value_ << std::endl;
    }

private:
    Counter() : value_(0) {}

private:
    int value_;
};

// a.cpp
Counter::GetInstance().Increase();

// b.cpp
Counter::GetInstance().Increase();

// c.cpp
Counter::GetInstance().Print();

Setelah mengimplementasikan pola Singleton, telah diimplementasikan satu instans global, dengan efek sama seperti variabel global, dan singleton memberikan pengelasan (encapsulation) yang lebih baik.

Kecuali: Kadang-kadang ruang lingkup variabel global hanya bersifat internal modul, sehingga akan ada banyak instance variabel global di ruang alur proses, setiap modul memiliki satu instans, skenario ini tidak dapat diselesaikan menggunakan pola Singleton.

7 Kelas

Konstruktor, Konstruktor Salin, Penugasan dan Fungsi Pembungkus

Konstruktor, salin, perpindahan dan fungsi pembungkus menyediakan metode pengelolaan siklus hidup objek:

  • Konstruktor (constructor): X()
  • Konstruktor salin (copy constructor): X(const X&)
  • Operasi penugasan salin (copy assignment): operator=(const X&)
  • Konstruktor perpindahan (move constructor): X(X&&) Diberikan C++11
  • Operasi penugasan perpindahan (move assignment): operator=(X&&) Diberikan C++11
  • Fungsi pembungkus (destructor): ~X()

Aturan 7.1.1 Variabel anggota kelas harus diinisialisasi secara eksplisit

Keterangan: Jika kelas memiliki variabel anggota, tidak mendefinisikan konstruktor, juga tidak mendefinisikan konstruktor default, kompiler akan secara otomatis menghasilkan konstruktor, namun konstruktor yang dihasilkan kompiler tidak akan melakukan inisialisasi pada variabel anggota, status objek berada dalam ketidakpastian.

Kecuali:

  • Jika variabel anggota kelas memiliki fungsi konstruktor default, maka tidak perlu inisialisasi eksplisit.

Contoh: Seperti kode berikut tidak ada konstruktor, data pribadi tidak dapat diinisialisasi:

Keterangan: Inisialisasi saat deklarasi C++11 dapat langsung terlihat nilai awal anggota, sebaiknya digunakan. Jika nilai inisialisasi anggota dan konstruktor berkaitan, atau tidak mendukung C++11, sebaiknya digunakan daftar inisialisasi konstruktor untuk menginisialisasi anggota. Berbanding dengan pada badan konstruktor untuk memberikan nilai anggota, kode daftar inisialisasi lebih ringan, performa eksekusi lebih baik, dan dapat untuk inisialisasi anggota const dan referensi.

    }

    unsigned char* msgBuffer_;

Aturan 7.1.2 Untuk menghindari konversi implisit, deklarasikan konstruktor satu parameter sebagai explicit

Keterangan: Jika konstruktor satu parameter tidak digunakan explicit, maka akan menjadi fungsi konversi implisit.

Contoh:

class Foo {
public:
    explicit Foo(const string& name): name_(name)
    {
    }
private:
    string name_;
};


void ProcessFoo(const Foo& foo){
}

int main(void)
{
    std::string test = "test";
    ProcessFoo(test);  // Kompilasi tidak melalui
    return 0;
}

Kode di atas tidak melalui kompilasi, karena ProcessFoo memerlukan parameter tipe Foo, tipe yang dimasukkan string tidak cocok.

Jika dikonstruktor Foo dikurangi kunci explicit, maka pemanggilan ProcessFoo dengan memasukkan string akan memicu konversi implisit, menghasilkan objek Foo sementara. Biasanya konversi implisit ini memukul kebingungan, dan mudah menyembunyikan Bug, serta mendapatkan konversi tipe yang tidak diinginkan. Oleh karena itu untuk konstruktor satu parameter dikehendaki deklarasi explicit.

Aturan 7.1.3 Jika tidak perlu konstruktor salin, operasi penugasan / konstruktor perpindahan, operasi penugasan, sebaiknya dilarang secara eksplisit

Keterangan: Jika pengguna tidak mendefinisikan, kompiler secara default akan menghasilkan konstruktor salin dan operasi penugasan salin, konstruktor perpindahan dan operasi penugasan perpindahan (fungsi semantik perpindahan C++11 kemudian ada). Jika kita tidak ingin menggunakan konstruktor salin, atau operasi penugasan, sebaiknya menolak secara eksplisit:

  2. Disarankan mewarisi NoCopyable, NoMovable, melarang menggunakan makro DISALLOW_COPY_AND_MOVE, DISALLOW_COPY, DISALLOW_MOVE dll.

}

Implementasi NoCopyable dan NoMovable:

class NoCopyable {
public:
    NoCopyable() = default;
    NoCopyable(const NoCopyable&) = delete;
    NoCopyable& operator = (NoCopyable&) = delete;
};

class NoMovable {
public:

    NoMovable(NoMovable&&) noexcept = delete;
    NoMovable& operator = (NoMovable&&) noexcept = delete;
}

Konstruktor salin dan operasi penugasan salin memiliki semantik salin, seharusnya muncul berpasangan atau dilarang.

Warisan Ganda

Dalam pengembangan nyata penggunaan warisan ganda adalah skenario yang relatif sedikit, karena adanya masalah tipikal berikut pada saat menggunakan warisan ganda:

  1. Warisan berkepinggayaan (diamond inheritance) yang membawa data duplikat, serta ketidakjelasan nama. Oleh karena itu, C++ memperkenalkan virtual inheritance untuk menyelesaikan masalah ini;
  2. Meski bukan warisan berkepinggayaan, nama beberapa kelas induk juga mungkin bertentangan, sehingga menyebabkan ketidakjelasan nama;
  3. Jika kelas turunan perlu memperluas atau mengubah metode beberapa kelas induk, menyebabkan tanggung jawab kelas turunan tidak jelas, semantik kabut;
  4. Berbanding dengan delegasi, warisan adalah kompleks white-box reuse, yaitu kelas turunan dapat mengakses protected anggota kelas induk, ini akan menyebabkan ketergantungan yang lebih kuat. Warisan ganda, berbanding dengan warisan tunggal, duekrut menghasilkan ketergantungan yang lebih kuat.

Warisan ganda memiliki keuntungan berikut: Warisan ganda menyediakan cara lebih sederhana untuk melakukan kombinasi untuk merealisasikan beberapa antarmuka atau penggabungan kelas.

Jadi, untuk warisan ganda hanya dalam kasus berikut diizinkan untuk digunakan.

Saran 7.3.1 Menggunakan warisan ganda untuk pemisahan antarmika dan kombinasi peran

Jika kelas tertentu perlu merealisasikan beberapa antarmuka, dapat melalui warisan ganda menggabungkan beberapa antarmika yang terpisah, mirip bahasa Scala traits campuran.

Overload

Operasi operator overload harus memiliki alasan yang cukup, dan jangan mengubah semantik operator asli, misalnya jangan menggunakan operator ‘+’ untuk melakukan operasi pengurangan.

Overload operator membuat kode lebih intuitif, namun juga memiliki beberapa kekurangan:

  • Mengabaikan intuisi, mengira operasi ini dan tipe bawaan sama adalah performa tinggi, mengabaikan kemungkinan penurunan performa;
  • saat penelusuran masalah, tidak intuitif, mencari nama fungsi lebih jelas daripada mencari operasi.
  • Overload operator jika perilaku didefinisikan tidak intuitif (misalnya menggunakan operator ‘+’ untuk melakukan operasi pengurangan), akan membuat kode menjadi membingungkan.
  • Overload operator penugasan menyebabkan konversi implisit yang tersembunyi bug yang sangat dalam. Dapat mendefinisikan fungsi seperti Equals(), CopyFrom() sebagai gantian operator =, ==.

Aturan 8.1.1 Hindari fungsi terlalu panjang, fungsi tidak melebihi 50 baris (non-komentar non-komentar)

Fungsi seharusnya dapat ditampilkan layar penuh (50 baris atau kurang), melakukan satu hal, dan melakukan hal itu dengan baik.

Fungsi terlalu panjang seringkali berarti fungsi memiliki fungsi tidak satu, terlalu kompleks, atau terlalu menampakkan detail, belum dilakukan abstraksi lebih lanjut.

Kecuali: Beberapa fungsi algoritma implementasi, karena agregat algoritma dan fungsi fitur penuh, mungkin akan melebihi 50 baris.

Meski fungsi panjang sekarang bekerja sangat baik, segera ada orang mengubahnya, kemungkinan muncul masalah baru, bahkan menyebabkan bug yang sulit dideteksi.

Saran memecahnya menjadi beberapa fungsi yang lebih singkat dan mudah dikelola, untuk memudahkan orang lain membaca dan mengubah kode.

Saran 8.2.1 Fungsi inline tidak melebihi 10 baris (non-komentar non-komentar)

Keterangan: Fungsa inline memiliki karakteristik umum fungsi, berbeda dengan fungsi umum hanya dalam penanganan pemanggilan fungsi. Ketika pemanggilaian fungsi umumnya, perlualihkan hak eksekusi ke fungsi yang dipanggil, lalu kembali ke fungsi yang memanggil; sedangkan fungsa inline saat pemanggilan, adalah mengganti ekspresi pemanggilan dengan badan fungsi inline.

Fungsi inline hanya cocok untuk fungsa kecil 1-10 baris. Untuk fungsi besar yang berisi banyak pernyataan, overhead pemanggilaian dan kembali fungsi relatif mikro, tidak ada alasan untuk menggunakan fungsi inline, mayoritas kompiler akan menolak cara inline, dan memilih cara pemanggilaian fungsi umum.

Jika fungsa inline berisi struktur kontrol kompleks, seperti perulangan, cabang (switch), try-catch dan sebagainya, mayoritas kompiler akan dianggap fungsi ini seolah-olah fungsa umum.

Fungsi virtual, fungsi rekursif tidak dapat digunakan sebagai fungsi inline.

Saran 8.3.1 Parameter fungsi gunakan referensi menggantikan pointer

Keterangan: Referensi lebih aman daripada pointer, karena pasti non-kosong, dan pasti tidak akan menunjuk ke target lain; referensi tidak perlu memeriksa pointer NULL ilegal.

Jika pengembangan produk berdasarkan platform lama, maka lebih tunduk urutan penanganan platform yang ada.

Pilih const untuk menghindari parameter dimodifikasi, membuat pembaca kode jelas parameter tidak dimodifikasi, dapat meningkatkan readability kode secara signifikan.

Konstanta dan Inisialisasi

Nilai yang tidak berubah lebih mudah dipahami, dipantau dan dianalisis, seharusnya se mungkin menggunakan konstanta menggantikan variabel, saat mendefinisikan nilai, seharusnya membuat const sebagai opsi default.

Aturan 9.1.1 Dilarang menggunakan makro untuk merujuk konstanta

Keterangan: Makro adalah penggantian teks sederhana, dilakukan pada fase preprocessor, saat error eksekusi langsung menampilkan nilai yang sesuai; saat debugging juga menampilkan nilai, bukan nama makro; makro tidak memiliki pengecekan tipe, tidak aman; makro tidak memiliki ruang lingkup.

#define MAX_MSISDN_LEN 20    // Tidak baik

// Untuk C++11 ke atas, dapat menggunakan constexpr

Saran 9.1.1 sekumpulan konstanta integer yang berkaitan harus didefinisikan sebagai enum

Keterangan: Enum lebih aman daripada #define atau const int. Kompilator akan memeriksa apakah nilai parameter berada dalam rentang nilai enum, menghindari kesalahan terjadi.

// Contoh yang baik:

    SUNDAY,
    MONDAY,
    TUESDAY,
    WEDNESDAY,
    THURSDAY,
    FRIDAY,

    BLACK,
    BLUE

// Contoh yang tidak baik:
const int SUNDAY = 0;
const int MONDAY = 1;

const int BLACK  = 0;
const int BLUE   = 1;

bool ColorizeCalendar(int today, int color);
ColorizeCalendar(BLUE, SUNDAY); // Tidak akan error

    DEV_DSMP = 0,
    DEV_ISMG = 1,
    DEV_WAPPORTAL = 2

Aturan 9.1.2 Dilarang menggunakan angka iblis

Angka iblis bermakna angka yang sul dipahami, sul dipahami.

Angka iblis bukanlah konsep hitam-putih, ada tingkat sul dipahami. Contoh angka 12, pada konteks berbeda situasi berbeda: type = 12; justru sul dipahami, tetapi monthsCount = yearsCount * 12; justru dipahami.

Angka 0 terkadang juga angka iblis, misalnya status = 0; tidak dapat mengekspresikan status apa.

Solusi: Untuk angka yang digunakan lokal, dapat menambahkan komentar penjelasan. Untuk angka yang digunakan berulang, harus mendefinisikan konstanta const, dan melalui nama simbol auto-comment.

Dilarang muncul situasi berikut: Tanpa melalui simbol untuk menjelaskan makna angka, seperti const int ZERO = 0 Nama simbol membatasi nilai ambilnya, seperti const int XX_TIMER_INTERVAL_300MS = 300, langsung gunakan XX_TIMER_INTERVAL_MS untuk menandakan konstanta ini adalah interval timer detik.

Aturan 9.1.3 Konstanta seharusnya memiliki tanggung jawab tunggal

Keterangan: Satu konstanta hanya digunakan untuk merepresentasikan satu fungsi tertentu, yaitu satu konstanta tidak boleh memiliki banyak tujuan.

// Contoh yang baik: Protokol A dan protokol B, panjang nomor telepon (MSISDN) keduanya 20.
const unsigned int A_MAX_MSISDN_LEN = 20;
const unsigned int B_MAX_MSISDN_LEN = 20;

// atau menggunakan nama namespace yang berbeda:
namespace Namespace1 {
    const unsigned int MAX_MSISDN_LEN = 20;
}

    const unsigned int MAX_MSISDN_LEN = 20;
}

Aturan 9.1.4 Dilarang menggunakan memcpy_s, memset_s untuk inisialisasi objek non-POD

Keterangan: POD adalah singkatan Plain Old Data, konsep yang diintroduksikan di standar C++ 98 (ISO/IEC 14882, first edition, 1998-09-01), tipe POD meliputi int, char, float, double, enumeration, void, pointer dan tipe primitif lainnya serta tipe agregat, tidak dapat menggunakan enkapsulasi dan fitur berorientasi objek (seperti konstruktor/penugasan/pembungkus pengguna definisikan, kelas dasar, fungsi virtual).

Karena tipe non-POD misalnya kelas non-agregat, kemungkinan ada fungsi virtual, layout memori tidak pasti, bergantung kompiler, penyalahgunakan operasi memori menyalin mungkin menyebabkan masalah serius.

Bahkan untuk kelas agregat, penggunaan menyalin memori langsung dan perbandingan, menghancurkan perlindungan informasi dan perlindungan data, tidak disarankan operasi memcpy_s, memset_s.

Untuk penjelasan POD lihat lampiran.

Saran 9.1.2 Variabel dideklarasikan saat digunakan dan diinisialisasi

Keterangan: Variabel sebelum digunakan belum diberi nilai, adalah kesalahan pemrograman tingkat rendah yang umum. Mendeklarasikan variabel saat digunakan dan sekaligus diinisialisasi, sangat memudahkan menghindari kesalahan jenis ini.

Mendeklarasikan semua variabel di posisi awal fungsi, kemudian digunakan variabel, ruang lingkup menutupi seluruh implementasi fungsi, mudah menyebabkan masalah berikut:

  • kode sul dipahami dan dipelihara: variabel didefinisikan dan digunakan terpisah.
  • variabel sul diinisialisasi dengan wajar: di posisi awal fungsi, seringkali tidak ada informasi cukup untuk inisialisasi variabel, seringkali digunakan nilai kosong default (misalnya nol) untuk inisialisasi variabel, ini biasanya adalah pemborosan, jika variabel digunakan sebelum diberikan nilai yang efektif, masih akan menyebabkan kesalahan.

Menurut prinsip ruang lingkup variabel paling minim dan prinsip deklarasi dekat, kode lebih mudah dibaca, memudahkan mengetahui tipe variabel dan nilai inisialisasi. Khususnya, sebaiknya menggunakan cara inisialisasi menggantikan deklarasi lalu penugasan.

// Contoh yang buruk: Deklarasi dan inisialisasi dipisahkan
string name;        // Deklarasi tanpa inisialisasi: memanggil konstruktor default
name = "zhangsan";  // Kemudian memanggil operasi penugasan; deklarasi dan definisi di tempat yang berbeda, dipahami relatif sulit

// Contoh yang baik: Deklarasi dan inisialisasi terintegrasi, dipahami relatif mudah
string name("zhangsan");  // Memanggil konstruktor

Ekspresi

Aturan 9.2.1 Ekspresi yang mengandung operasi increment atau decrement variabel dilarang lagi merujuk variabel tersebut

Ekspresi yang mengandung operasi increment atau decrement variabel, jika lagi merujuk variabel tersebut, hasilnya dalam standar C++ tidak ditentukan secara eksplisit. Setiap kompiler atau versi kompiler yang sama mungkin implementasi tidak konsisten.

Untuk portabilitas yang lebih baik, seharusnya tidak membuat asumsi apapun tentang urutan operasi.

Catatan, masalah urutan operasi tidak dapat diselesaikan dengan tanda kurung, karena ini bukan masalah prioritas.

Contoh:

x = b[i] + i++; // Bad: operasi b[i] dengan i++, urutan tidak jelas

Cara yang benar adalah meletakkan operasi increment atau decrement satu baris terpisah:

x = b[i] + i;
i++;            // Good: satu baris terpisah

Parameter fungsi

Func(i++, i);   // Bad: saat memparameter kedua tidak pasti operasi increment sudah terjadi atau tidak

Cara yang benar

i++;            // Good: satu baris terpisah
x = Func(i, i);

Aturan 9.2.2 Switch statement harus memiliki branch default

Sebagian besar kasus, switch statement harus memiliki branch default, untuk memastikan saat label case terlewak ditangani dapat memiliki perilaku default.

Kecuali: Jika variabel kondisi switch adalah tipe enum, dan case branch menutup semua nilai, maka menambahkan branch default sedikit redundan. Kompilator modern semua memiliki kemampuan untuk memeriksa apakah di dalam switch statement ada case branch yang terlewat nilai enum tertentu, akan ada peringatan (warning) sesuai.

enum Color {
    RED = 0,
    BLUE
};

// Karena variabel kondisi switch adalah nilai enum, di sini dapat tidak menambahkan branch default
switch (color) {
    case RED:
        DoRedThing();
        break;
    case BLUE:
        DoBlueThing();
        ...
        break;
}

Saran 9.2.1 Ekspresi perbandingan, seharusnya mengikuti prinsip miring ke kiri bergantung perubahan, miring ke kanan bergantung tidak berubah

Saat variabel dibandingkan dengan konstanta, jika konstanta diletakkan di kiri, seperti if (MAX == v) tidak sesuai dengan kebiasaan membaca, sedangkan if (MAX > v) lebih sul dipahami.

Seharusnya mengikuti kebiasaan membaca manusia, ekspresi normal, letakkan konstanta di kanan.

Tulislah seperti berikut:

if (value == MAX) {

}

if (value < MAX) {

}

Ada kasus khusus, seperti: if (MIN < value && value < MAX) digunakan untuk mendeskripsikan interval, di bagian awal konstanta di kiri.

Jangan khawatir if (value = MAX) salah ketik menjadi =, karena if (value = MAX) akan ada peringatan kompilasi, alat statis cek kode juga akan melaporkan kesalahan. Biarkan alat menyelesaikan masalah ketik salah, kode harus mengutamakan readability.

Saran 9.2.2 Gunakan tanda kurung untuk menjelaskan prioritas operator

Gunakan tanda kurung untuk menjelaskan prioritas operator, menghindari karena prioritas default tidak sesuai dengan pemikiran desain menyebabkan program salah; sekaligus kode lebih jelas dan bisa dibaca, namun terlalu banyak tanda kurung akan membagi kode sehingga readability menurun. Berikut adalah saran penggunaan tanda kurung.

  • Operator biner dan lebih dari, jika melibatkan banyak operator, seharusnya gunakan tanda kurung
x = a + b + c;         /* operator sama, dapat tidak menambahkan tanda kurung */
x = Foo(a + b, c);     /* di kedua sisi tanda koma ekspresi, tidak perlu tanda kurung */
x = 1 << (2 + 3);      /* operator berbeda, perlu tanda kurung */
x = a + (b / 5);       /* operator berbeda, perlu tanda kurung */
x = (a == b) ? a : (a – b);    /* operator berbeda, perlu tanda kurung */

规则9.4.1 单个对象释放使用delete，数组对象释放使用delete [] 说明：

单个对象删除使用delete， 数组对象删除使用delete []，原因：

  • 调用new所包含的动作：从系统中申请一块内存，并调用此类型的构造函数。
  • 调用new[n]所包含的动作：申请可容纳n个对象的内存，并且对每一个对象调用其构造函数。
  • 调用delete所包含的动作：先调用相应的析构函数，再将内存归还系统。
  • 调用delete[]所包含的动作：对每一个对象调用析构函数，再释放所有内存 如果new和delete的格式不匹配，结果是未知的。对于非class类型， new和delete不会调用构造与析构函数。

... 
delete numberArray; 
numberArray = nullptr;

正确写法：

const int MAX_ARRAY_SIZE = 100; 
int* numberArray = new int[MAX_ARRAY_SIZE]; 
... 
delete[] numberArray; 
numberArray = nullptr;

规则9.5.1 不要保存std::string的c_str()返回的指针

说明：在C++标准中并未规定string::c_str()指针持久有效，因此特定STL实现完全可以在调用string::c_str()时返回一个临时存储区并很快释放。所以为了保证程序的可移植性，不要保存string::c_str()的结果，而是在每次需要时直接调用。 示例：

    const char* text = name.c_str();  // 表达式结束以后，name的生命周期还在，指针有效 

    // 如果中间调用了string的非const成员函数，导致string被修改，比如operator[], begin()等 
    // 可能会导致text的内容不可用，或者不是原来的字符串 
    name = "test";

} 

void Fun2()

例外：在少数对性能要求非常高的代码中，为了适配已有的只接受const char*类型入参的函数，可以临时保存string::c_str()返回的指针。但是必须严格保证string对象的生命周期长于所保存指针的生命周期，并且保证在所保存指针的生命周期内，string对象不会被修改。

建议9.5.1 使用std::string代替char*

说明：使用string代替char*有很多优势，比如：

  1. 不用考虑结尾的’\0’；
  2. 可以直接使用+, =, ==等运算符以及其它字符串操作函数；
  3. 不需要考虑内存分配操作，避免了显式的new/delete，以及由此导致的错误；

需要注意的是某些stl实现中string是基于写时复制策略的，这会带来2个问题，一是某些版本的写时复制策略没有实现线程安全，在多线程环境下会引起程序崩溃；二是当与动态链接库相互传递基于写时复制策略的string时，由于引用计数在动态链接库被卸载时无法减少可能导致悬挂指针。因此，慎重选择一个可靠的stl实现对于保证程序稳定是很重要的。 例外： 当调用系统或者其它第三方库的API时，针对已经定义好的接口，只能使用char*。但是在调用接口之前都可以使用string，在调用接口时使用string::c_str()获得字符指针。 当在栈上分配字符数组当作缓冲区使用时，可以直接定义字符数组，不要使用string，也没有必要使用类似vector<char>等容器。

说明：在stl库中的std::auto_ptr具有一个隐式的所有权转移行为，如下代码：

### <a name="r10-1-1"></a>规则10.1.1 在重写虚函数时请使用`override`或`final`关键字 
**理由** 
`override`和`final`关键字都能保证函数是虚函数，且重写了基类的虚函数。如果子类函数与基类函数原型不一致，则产生编译告警。`final`还保证虚函数不会再被子类重写。 
使用`override`或`final`关键字后，如果修改了基类虚函数原型，但忘记修改子类重写的虚函数，在编译期就可以发现。也可以避免有多个子类时，重写虚函数的修改遗漏。 

**示例** 

```cpp 
class Base { 
public: 
    virtual void Foo(); 
    virtual void Foo(int var); 
    void Bar(); 
}; 

class Derived : public Base { 
public: 
    void Foo() const override; // 编译失败: Derived::Foo 和 Base::Foo 原型不一致，不是重写 
    void Foo() override;       // 正确: Derived::Foo 重写 Base::Foo 
    void Foo(int var) final;   // 正确: Derived::Foo(int) 重写 Base::Foo(int)，且Derived的派生类不能再重写此函数 
    void Bar() override;       // 编译失败: Base::Bar 不是虚函数 
};

总结

  1. 基类首次定义虚函数，使用virtual关键字
  2. 子类重写基类虚函数（包括析构函数），使用override或final关键字（但不要两者一起使用），并且不使用virtual关键字
  3. 非虚函数，virtual、override和final都不使用

规则10.1.3 使用nullptr，而不是NULL或0

理由 长期以来，C++没有一个代表空指针的关键字，这是一件很尴尬的事：

#define NULL ((void *)0)

void(C::*pmf)() = &C::Func; 
if (pmf == NULL) {} // 错误: void* 不能自动转换为指向成员函数的指针

如果把NULL被定义为0或0L。可以解决上面的问题。 或者在需要空指针的地方直接使用0。但这引入另一个问题，代码不清晰，特别是使用auto自动推导：

auto result = Find(id); 
if (result == 0) {  // Find() 返回的是 指针 还是 整数? 
    // do something 
}

0字面上是int类型(0L是long)，所以NULL和0都不是指针类型。 当重载指针和整数类型的函数时，传递NULL或0都调用到整数类型重载的函数:

void F(int); 
void F(int*); 

F(0);      // 调用 F(int)，而非 F(int*) 
F(NULL);   // 调用 F(int)，而非 F(int*)

另外，sizeof(NULL) == sizeof(void*)并不一定总是成立的，这也是一个潜在的风险。 总结： 直接使用0或0L，代码不清晰，且无法做到类型安全；使用NULL无法做到类型安全。这些都是潜在的风险。 nullptr的优势不仅仅是在字面上代表了空指针，使代码清晰，而且它不再是一个整数类型。

nullptr是std::nullptr_t类型，而std::nullptr_t可以隐式的转换为所有的原始指针类型，这使得nullptr可以表现成指向任意类型的空指针。

void F(int); 
void F(int*); 
F(nullptr);   // 调用 F(int*) 

auto result = Find(id); 
if (result == nullptr) {  // Find() 返回的是 指针 
    // do something 
}

规则10.1.5 禁止使用std::move操作const对象

从字面上看，std::move的意思是要移动一个对象。而const对象是不允许修改的，自然也无法移动。因此用std::move操作const对象会给代码阅读者带来困惑。 在实际功能上，std::move会把对象转换成右值引用类型；对于const对象，会将其转换成const的右值引用。由于极少有类型会定义以const右值引用为参数的移动构造函数和移动赋值操作符，因此代码实际功能往往退化成了对象拷贝而不是对象移动，带来了性能上的损失。

错误示例：

std::vector<std::string> g_stringList; 

void func() 
{ 
    const std::string myString = "String content"; 
    g_string = std::move(myString); // bad:并没有移动myString，而是进行了复制 
    const std::string anotherString = "Another string content"; 
    g_stringList.push_back(std::move(anotherString));    // bad:并没有移动anotherString，而是进行了复制 
}

规则10.2.2 使用std::make_unique而不是new创建unique_ptr

理由

  1. make_unique提供了更简洁的创建方式
  2. 保证了复杂表达式的异常安全

示例

std::unique_ptr<MyClass> ptr(new MyClass(0, 1)); 
// 好：只出现一次 MyClass，不存在不一致的可能 

n auto ptr = std::make_unique<MyClass>(0, 1);

重复出现类型可能导致非常严重的问题，且很难发现：

// 编译正确，但new和delete不配套

// 非异常安全: 编译器可能按如下顺序计算参数: 
// 1. 分配 Foo 的内存, 
// 2. 构造 Foo, 
// 3. 调用 Bar, 
// 4. 构造 unique_ptr<Foo>.

理由 使用std::make_shared除了类似std::make_unique一致性等原因外，还有性能的因素。 std::shared_ptr管理两个实体：

  • 管理对象

规则10.3.1 非局部范围使用lambdas，避免使用按引用捕获

理由 非局部范围使用lambdas包括返回值，存储在堆上，或者传递给其它线程。局部的指针和引用不应该在它们的范围外存在。lambdas按引用捕获就是把局部对象的引用存储起来。如果这会导致超过局部变量生命周期的引用存在，则不应该按引用捕获。

示例

// 不好 
void Foo() 
{ 
    int local = 42; 
    // 按引用捕获 local. 
    // 当函数返回后，local 不再存在， 
    // 因此 Process() 的行为未定义! 
    threadPool.QueueWork([&]{ Process(local); }); 
} 

// 好 
void Foo() 
{ 
    int local = 42; 
    // 按值捕获 local。 
    // 因为拷贝，Process() 调用过程中，local 总是有效的 
    threadPool.QueueWork([=]{ Process(local); }); 
}

建议10.3.2 如果捕获this，则显式捕获所有变量

理由 在成员函数中的[=]看起来是按值捕获。但因为是隐式的按值获取了this指针，并能够操作所有成员变量，数据成员实际上是按引用捕获的，一般情况下建议避免。如果的确需要这样做，明确写出对this的捕获。

示例

class MyClass { 
public: 
    void Foo() 
    { 
        int i = 0; 

        auto Lambda = [=]() { Use(i, data_); };   // 不好: 看起来像是拷贝/按值捕获，成员变量实际上是按引用捕获 

        data_ = 42; 
        Lambda(); // 调用 use(42); 
        data_ = 43; 
        Lambda(); // 调用 use(43); 

        auto Lambda2 = [i, this]() { Use(i, data_); }; // 好，显式指定按值捕获，最明确，最少的混淆 
    } 

private: 
    int data_ = 0; 
};

建议10.3.3 避免使用默认捕获模式

理由 lambda表达式提供了两种默认捕获模式：按引用（&）和按值（=）。 默认按引用捕获会隐式的捕获所有局部变量的引用，容易导致访问悬空引用。相比之下，显式的写出需要捕获的变量可以更易的检查对象生命周期，减小犯错可能。 默认按值捕获会隐式的捕获this指针，且难以看出lambda函数所依赖的变量是哪些。如果存在静态变量，还会让阅读者误以为lambda拷贝了一份静态变量。 因此，通常应当明确写出lambda需要捕获的变量，而不是使用默认捕获模式。

错误示例

auto func() 
{ 
    int addend = 5; 
    static int baseValue = 3; 

    return [=]() {  // 实际上只复制了addend 
        ++baseValue;    // 修改会影响静态变量的值 
        return baseValue + addend; 
    }; 
}

正确示例

auto func() 
{ 
    int addend = 5; 
    static int baseValue = 3; 

    return [addend, baseValue = baseValue]() mutable {  // 使用C++14的捕获初始化拷贝一份变量 
        ++baseValue;    // 修改自己的拷贝，不会影响静态变量的值 
        return baseValue + addend; 
    }; 
}
